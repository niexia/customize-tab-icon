# Documentation

<!-- release: 1.1.0 -->

Changicon's documentation is part of the product. It is updated in the same
change as the behavior it describes. `scripts/release-docs.test.ts` runs in
`pnpm test` and fails the build when a release marker, changelog entry, or store
asset is stale.

## Index

| Document | What it covers | Update when |
| --- | --- | --- |
| [Architecture](architecture.md) | Runtime topology, storage schema, apply/reset/migration sequences, favicon DOM state machine, security, known limitations | Any behavior, storage, permission, or flow change |
| [Release process](release-process.md) | Versioning, Conventional Commits, changelog, checks, tag/release workflow, Chrome Web Store submission, rollback | Any release/process change |
| [AGENTS.md](AGENTS.md) | Rules for agents editing this directory | The docs workflow changes |
| [`../store/README.md`](../store/README.md) | Store kit: listing copy, asset map, permission/privacy answers, reviewer steps, checklist, and the public privacy policy | Features, permissions, data handling, or asset requirements change |

## Screenshots and diagrams

- **Diagrams:** Mermaid inside Markdown. GitHub renders them; keep the source in
  the document rather than committing a separate image so it can be reviewed and
  edited. Use `flowchart` for structure, `sequenceDiagram` for protocol/order,
  and `stateDiagram-v2` for DOM/lifecycle states.
- **Product images:** `docs/screenshots/` holds 2× popup captures for the README.
  They are generated by `pnpm store:assets` from the real popup bundle; do not
  edit them by hand.
- **Store images:** `store/assets/` holds the exact-size dashboard assets. Their
  dimensions and alpha rules are checked by the release-docs test.

## Legacy assets

Pre-1.1.0 design, showcase, and flow images are kept in
[`legacy/`](legacy/README.md) for history. They are not current and should not be
used in the README or store listing.

## Release marker

`architecture.md`, `release-process.md`, and `store/README.md` carry
`<!-- release: X.Y.Z -->`. The marker records the version the document was last
verified against. Bump it in the release commit after reviewing the document;
the release-docs test compares it with `package.json`.

## Writing style

- Explain the **why** and the invariants, not only the file list.
- Keep code paths and storage keys exact; link to the source file when useful.
- Use present tense and short paragraphs.
- Prefer a table or a diagram over a long prose list.
- If something is a limitation, say so explicitly rather than implying it works.

## Validating

```bash
pnpm test
# or only the release checks:
pnpm exec vitest run scripts/release-docs.test.ts
```

The release-docs checks verify required files, the release markers, the changelog
entry, the five store screenshots at 1280×800, the promo tiles, the store icon,
the single-document store kit, and relative links inside the docs. They do not
validate Mermaid rendering; preview the diagram on GitHub or in an IDE before
merging.
